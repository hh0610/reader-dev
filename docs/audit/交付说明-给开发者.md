## 一、起点与工作方式

**起点是一条生产反馈**：网络书源搜索正常、能搜到书，但点进去没有目录。

顺着这一条查下去，发现的不是一个孤立 bug，而是一类模式：**书源规则解析失败时静默返回
`isSuccess: true` + 空数据**，于是用户看到的是空白，服务端日志里什么也没有。这条主线牵出了
后面大部分工作。

工作分三个阶段推进，每个阶段的发现方式不同，也决定了它们各自能抓到什么：

| 阶段 | 方式 | 抓到的问题类型 |
| --- | --- | --- |
| 一、对抗性审计 | 通读代码 + 构造边界输入 | 安全面（越权/穿越/SSRF/panic）、静默失败簇 |
| 二、真机实测 | 起服务、导入真实 EPUB/PDF、接 316 个书源逐项点 | **单测全绿但真跑就错**的问题（占次轮全部发现） |
| 三、对比调研 | 读 komga-cn 与 booklore 源码，挑可借鉴的做法 | 架构级改进 + 顺带翻出的既有问题 |

第二阶段值得单独说一句：**次轮的每一个发现都是真机点出来的，没有一个是靠读代码想出来的**。
包括我自己在第一阶段引入的 3 处回归。这也是为什么第三阶段每做完一项都要重新起服务实测。

## 三、架构级改动（升级前务必读）

### 3.1 正文图片：从 base64 内联改为按需从原压缩包取

**改动前**：EPUB/CBZ 的图片在导入时 base64 内联进章节文本存库。
代价是 base64 本身多占 33%、整章一次性传完才显示、浏览器无法缓存单张图、
且受 `MAX_EPUB_INLINE_IMAGE_BYTES`(80MB) 限制——**超预算的图是被静默丢弃的**。

**改动后**：正文只存地址 `![alt](/book-asset?url={bookUrl}&path={条目})`，
图片由新端点从**原始压缩包**流出。

实测：4.51MB 的轻小说、24 章含彩插，章节文本入库 **83.7KB**（内联时约 6MB）。

**范围刻意收窄**：只有「章节会入库、原文件会长期留存」的四条路径启用
（uploadLocalBook / scanLocalBookDir / 双轨自动导入 / 文件修改重扫）；
导出、预览、OPDS 拼接等一次性用途仍旧内联——那些结果离开服务端后没法再回来取图。
PDF 转图片书也保持内联：它的图来自 PDF 对象而非压缩包条目，端点无从按路径取。

**鉴权（前端一行未改）**：浏览器发 `<img>` 子请求不会带 Authorization 头。
`getBookContent` 这一次请求本身是带鉴权的，就借它下发 `Path=/book-asset` 的
HttpOnly cookie，后续图片请求自动携带；端点同时接受 query token。

**安全**：条目路径不落文件系统，只在压缩包内查找——**压缩包自身的条目表就是白名单**；
只服务图片类型，非图片条目一律 404，不让这个端点变成任意读取压缩包内容的通道；
书必须属于该命名空间。

> **部署影响**：新导入的本地书，**原文件必须留在原处**，删掉会导致图片 404（文字仍可读）。
> 上传导入的原件落在 `data/{ns}/opds_files/`。**老数据不受影响**（已入库的 data URI 照常显示）。

### 3.2 新增端点

| 端点 | 用途 | 鉴权 |
| --- | --- | --- |
| `GET /book-asset?url=&path=` | 正文图片按需取 | token 或路径限定 cookie |
| `GET /cover-thumb/{ns}/{file}` | 封面缩略图（按需生成 + 落盘缓存） | 与 `/assets` 一致（当前不鉴权） |

反向代理若按路径白名单转发，需一并放行。

`/cover-thumb` 的鉴权选择是刻意的：封面本就经 `/assets/{ns}/covers/*` 明文可取，
这里单独加一道不提高保密性，反而会让 `<img>` 加载失败。`/assets` 的鉴权是既有待办（见 §6），
届时两处一起改。

### 3.3 数据库新增列

| 表 | 列 | 用途 |
| --- | --- | --- |
| `books` | `file_hash` | 导入去重指纹 |
| `books` | `locked_fields` | 元数据字段锁 |

幂等 `ensure_column` 自动补，旧库无需手工迁移。

⚠️ **注意 `INSERT OR REPLACE` 会重置未列出的列**。`upsert_book` 与 `save_local_book`
都必须显式写回这两列——这个坑本轮踩过一次：不写回的话，**任何一次 saveBook
（包括每次阅读进度回写）都会静默清掉去重指纹**，功能直接失效。已加回归测试锁住。
后续若再给 books 加列，请一并检查这两个函数。

### 3.4 书籍 JSON 新增只读字段

`thumbUrl`、`metaScore`、`metaMissing`、`lockedFields`。
均为服务端计算/维护，客户端传什么都不生效。老客户端忽略即可，不影响既有字段。

## 四、存量数据需要手工处理的两件事

修复只管**新数据**，存量库需要各清一次。

### 4.1 `opds_files` 孤儿文件

**问题**：「移出书架时连同导入副本一并删除」删的是 `book.local_file`，
那指向的是**双轨同步生成到书仓的 epub**，而不是上传时落在
`data/{ns}/opds_files/{uuid}.{ext}` 的原件。结果每上传一本书就永久留下一份原文件。

实测一个演示库：在架本地书 2 本，`opds_files` 里 15 个文件 118MB，
其中 **13 个共 112MB 是书早已删除的孤儿**。

**清理规则**：`opds_files/` 下文件名（去扩展名）在 `books` 表里没有对应
`local://{文件名}` 记录的，即为孤儿，可删。

⚠️ 扫描导入的书是 `local://store/{hash}`，**没有上传副本**，它的原件是用户自己放在
书仓/目录里的文件，**不得删除**。修复后的代码也只处理 `local://{uuid}` 形态。

### 4.2 `book_vars_cache` 膨胀（影响最大，建议先自查）

**问题**：目录解析会把整页 HTML 塞进 `vars["src"]` 供 JS 规则求值，
而落库时把整个 map 原样写入，且**每个章节各存一份**——一页 100 章的目录
就是同一份页面 HTML 落库 100 次。这张表还从来没有过清理机制（`updated_at` 列
写了却从来没被读过）。

这不只是体积问题，**也是正确性问题**：下次求值若命中这份陈旧的 `src`，
规则读到的是上一次请求的页面。

实测一个只读过几本书的演示库：`reader.db` **1.1GB**，其中
`book_vars_cache` 占 **970MB / 13558 行**（平均 64KB/行，最大单行 299KB）。
再叠加「每次启动全量备份、保留 5 份」（GAP 148 迁移前快照，设计本身没问题），
磁盘占用是它的 6 倍。

**自查**：

```sql
SELECT count(*), sum(length(vars_json))/1024/1024 AS mb FROM book_vars_cache;
```

**清理**（清空该表是安全的，丢的只是 `@put` 变量缓存，下次求值会重新写入）：

```sql
DELETE FROM book_vars_cache;
VACUUM;    -- 必须，否则 SQLite 不把空间还给操作系统，库文件大小纹丝不动
```

演示库实测：清理 + VACUUM 后 **1.1GB → 4.9MB**。

**修复后**：`src` / `result` / `baseUrl` 这类瞬态上下文不再入缓存；单值上限 32KB；
保留期由 env `READER_BOOK_VARS_KEEP_DAYS` 控制（默认 30 天，`<=0` 关闭），
挂在每日自动备份**之后**执行——放在备份后是有意的，万一清错了当天备份里还有。

同一次取 875 章目录的实测对比：修前写入约 55MB，修后 1KB。

## 五、其它行为变更

这几处改变了**对外可观察行为**，升级时请确认符合预期：

1. **解析为空 → 明确业务错误**（此前 `isSuccess:true` + 空数据）。
   前端若依赖「成功但空」展示空态，需同步调整。
2. **secure 模式收紧**（非 secure 单用户模式行为不变）：MongoDB 备份/恢复需管理员或
   secureKey；`/epub`、`/book-assets` 需 token 且 URL 首段命名空间必须匹配；
   `getSystemInfo` / `getServerStats` 需登录。
3. **爬虫响应体上限** `READER_HTTP_MAX_BYTES`（默认 32 MiB），超限报错。
   若有书源返回超大响应需调大。
4. **多源搜索单源超时 25 秒**：极慢书源不再拖垮整批搜索，但其结果会缺失。
5. **正文分页上限 5 → 20**：超长分页章节不再被静默截断。
6. **PDF 正文排版重排**：lopdf 按绘制指令逐段输出（视觉一行被切成多段、标点单独成行），
   现拼回自然段并支持跨页续写。同一 PDF 导入后的章节内容与此前不同（更可读）。
   已知限制：文档首部的标题/作者/日期行会并入首段——缺少版面坐标信息无法可靠区分。
7. **EPUB 章节标题**：spine 标题若与书名雷同视为占位符，由 toc 真实章名覆盖
   （Calibre 产物此前会出现「整本书每章都叫书名」）。
8. **重复上传同一文件不再新建书**，直接返回原书；确需重导入用 `?force=1`。
9. **删书会回收导入落盘的文件**（上传原件 + 封面 + 缩略图 + 双轨生成的 epub）。

### 数据迁移

`user_namespace='default'` 的行，按 `books` 表归属改写为真实用户命名空间。
**仅回填「恰好属于唯一一个非 default 命名空间」的书**；共享书与本就属于 default 的

## 六、已知限制 / 未做

1. **`/assets` 静态目录仍未鉴权**：UI 上传的背景图经 CSS `url()` 加载，无法携带 token，
   强制鉴权会破坏功能。书籍正文（更敏感）已由 `/epub`、`/book-assets` 的命名空间校验覆盖。
   彻底方案需签名 URL，改动较大。
2. **源书正文缓存无 TTL / 不识别「坏数据」**：空正文已不再缓存；但非空的风控页/占位文本
   仍会被缓存。识别「坏」易误伤合法短章节，且加 TTL 需给 `book_chapters` 加列，
   留待产品定义判据。
3. **PDF 封面仅支持内嵌 JPEG/JP2**：纯 lopdf 方案、零新增依赖，对扫描版 PDF 有效；
   矢量排版页无内嵌图则无封面。升级为整页渲染需引入 pdfium 原生库。
4. **PDF 内嵌 JPEG2000 / JBIG2 解不开**：这是 PDF 解析的通病（booklore 用 PDFBox
   也要外挂 `jai-imageio-jpeg2000` 与 `jbig2-imageio`）。扫描版 PDF 若用这两种编码，
   转图片书会失败。
5. **EPUB3 扩展元数据未接**：作者角色、系列、阅读方向、landmarks 等，
   `OpfMeta` 无对应字段，需先扩数据模型与前端展示。
6. **重定向仍有 SSRF rebinding 残余**：入口 host 已钉死校验过的 IP，但 reqwest 内部发起的
   重定向连接无法逐跳钉 IP（已在 `ssrf_redirect_policy` 注释说明），每跳仍做公网校验。
7. **`/book-asset` 每次请求重开压缩包**：一章 30 张图就重解 30 次中央目录。
   booklore 有同样的问题。当前靠 `Cache-Control: private, max-age=604800` 让浏览器
   只取一次兜住；若成为瓶颈，可加条目偏移量的 LRU 缓存。

## 八、应用方式

见 `patches/如何应用.txt`。推荐 `git bundle`（保留完整提交信息与作者）：

```bash
git bundle verify reader-dev-fixes.bundle
git fetch /绝对路径/reader-dev-fixes.bundle fix/toc-empty-onclick-bookurl:fix-audit
git log --oneline master..fix-audit    # 应看到 49 个提交
git merge fix-audit
```

备选：`git apply patches/*.patch`（先 `--check` 干跑）。

注：部分 git 版本（实测 Apple Git 2.50.1）对本组 `.patch` 执行 `git am` 会误报冲突，
但 `git apply` 正常、diff 本身无误。bundle 方式不受影响，优先用 bundle。

`patches/bin/reader-dev-linux-x64.zip` 是与本组补丁同一份代码的 x86_64 Linux
静态链接二进制（musl，已 strip，前端已内嵌）：

```bash
READER_APP_SECURE=true READER_SERVER_PORT=8080 ./reader-dev
```

## 九、验证方式说明

后端 826 个测试、前端 103 个测试全绿，但**测试全绿不等于功能可用**——
本轮次轮的每一个发现都是真机点出来的，其中有单测全绿、真跑就 404 的情况（见 §7 第 4 条）。
所以每一项改动都做了这样一轮：

1. `cargo test --lib` + `node --test` + `vue-tsc`
2. 编译 release 二进制、起服务、导入真实文件（用户提供的 EPUB / PDF / 316 个书源订阅）
3. 用 headless Chrome 打开真实页面，检查渲染与网络请求
4. 对新端点做一轮对抗性自查（路径穿越、跨命名空间、伪造字段写入）

新增测试若涉及「防回归」，都验证过**去掉修复后该测试确实会失败**，避免写出空跑的用例。
