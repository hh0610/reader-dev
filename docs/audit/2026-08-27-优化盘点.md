# 优化盘点（2026-08-27，41 个提交交付后）

> 目的：功能与安全轮做完之后，专门盘一遍「还不够好」的地方。
> 每项都实际验证过（编译警告逐条看过出处、SQL 逐条 `EXPLAIN QUERY PLAN`、
> chunk 逐个量过 gzip 体积），不是猜的清单。
>
> 结论先行：**没有发现新的正确性/安全问题**；剩下的是性能与工程卫生，
> 按收益/成本排序如下。

---

## 一、值得做（按收益/成本排序）

### 1. 前端首屏体积 —— 最大的一块

实测（gzip 后）：

| chunk | gzip | 原因 |
| --- | --- | --- |
| `index-*.js` | **343 KB** | `main.ts` 里 `import ElementPlus from 'element-plus'` **全量引入** + 全量 CSS |
| `hanMode-*.js` | **438 KB** | `chinese.ts` 内嵌整套 OpenCC 简繁词典（约 1MB 源码），被 6 个视图**静态引入** |

两个问题、两个改法：

- **element-plus 改按需**（`unplugin-vue-components` + `ElementPlusResolver`）。
  项目实际用到的组件有限，全量引入把没用到的组件和样式全打进主包。
  预估主包可砍掉一半以上。改动集中在 `main.ts` + `vite.config.ts`，
  风险点是个别通过 `ElMessage` 等 API 方式调用的组件需要显式引样式。
- **简繁词典改懒加载**。`hanMode.ts` 静态 `import` 词典 →
  改为 `await import('./chinese.ts')`，且 `mode === 'auto'`（默认，不转换）时**根本不加载**。
  现状是用户第一次进搜索/阅读/探索任一页面就要拉 438KB gzip，
  而多数用户从未切过简繁。需要处理的一点：`applyHan` 是同步调用，
  懒加载后首次切换需要一个「词典就绪后重渲染」的小状态。

> 参照：hls.js（578KB）已经是动态 `import` 了——词典照这个既有模式改即可。

### 2. 数据库缺索引 —— 三行 SQL 的事

`EXPLAIN QUERY PLAN` 实测，**全库没有一个显式索引**，以下高频查询在全表扫描：

| 查询 | 现状 | 触发频率 |
| --- | --- | --- |
| `find_book_by_file_hash` | `SCAN books` | **每次上传**（导入去重） |
| `find_book_by_name_author` | `SCAN books` | **每次 saveBook**（换源判重） |
| `get_book_sources` 按 ns | `SCAN book_sources` | 每次搜索/换源 |

书架几十本时无感，几百本 + 多用户时这三条都是线性劣化。修法是启动时
`CREATE INDEX IF NOT EXISTS`（项目已有 `ensure_column` 的幂等模式，照抄即可）：

```sql
CREATE INDEX IF NOT EXISTS idx_books_ns_hash   ON books(user_namespace, file_hash);
CREATE INDEX IF NOT EXISTS idx_books_ns_name   ON books(user_namespace, name, author);
CREATE INDEX IF NOT EXISTS idx_sources_ns      ON book_sources(user_namespace);
```

其余高频路径已由主键自动索引覆盖（逐条验过）：`books(book_url, user_namespace)`、
`book_chapters(book_url, chapter_index, user_namespace)`、`toc_cache`、`book_vars_cache` ✓。

### 3. 书架更新检查是串行的

`run_shelf_update` 对全部可更新的网络书**逐本串行**抓目录。50 本网络书、
慢源占几本的话，一轮检查要跑几分钟（每本最长吃满超时）。
早前用户遇到的「下拉刷新 15 秒超时」根子上也与此相关（当时修的是前端误触发）。

改法：有界并发（4~8，`Semaphore`，比照搜索已有的 24 并发模式）+ 单书超时。
串行对源站温柔是优点，所以并发数别学搜索开 24。

### 4. 编译警告清零（16 条）

- **6 处 `unused variable: namespace`**（add_user / get_users / update_user /
  reset_user_password / cancel_cache_book / save_opds_settings）：
  逐处核实过——都是把 `resolve_namespace` 当**登录门槛**用，后续走
  `check_manager_auth` 或按显式 username 操作，**不是漏过滤**。
  但这个写法让每个读代码的人都要重新核实一遍，改成
  `let _namespace = ...`（或抽个 `require_login()`）把意图写明。
- **2 处 deprecated**：quick-xml `unescape_value` → `normalized_value()`。
- 其余 8 条（unused import/fn、无谓 `mut`）`cargo fix` 可自动处理一半，
  never-used 函数需人工确认是「留作对齐 legacy 的接口」还是真死代码。

### 5. `/book-asset` 每次请求重开压缩包（已知，条件触发再做）

一章 30 张图 = 重解 30 次 zip 中央目录。当前靠 `Cache-Control: max-age=604800`
让浏览器只取一次兜住，日常无感。若日后出现「多用户同时首读同一本图多的书」的
场景，再加 (路径, mtime) → 条目偏移表的小 LRU。**现在不动**——加缓存就要处理
失效，成本大于当下收益。

## 二、盘过、确认不用动的

| 项 | 结论 |
| --- | --- |
| release profile | `lto = true` + `strip = true` + `codegen-units = 1` 已是最优配置 ✓ |
| 搜索并发 | Semaphore(24) 封顶 ✓ |
| `source.put` / js_cache | 单源 1000 条 / 1MB 上限 ✓ |
| 图片代理缓存 | 磁盘 LRU + 容量上限（512MB 可调）✓ |
| hls.js | 已动态 import，不进首屏 ✓ |
| 全书搜索 | 仅本地书、SQL LIKE，规模可控 ✓ |
| `book_vars_cache` | 本轮已修（瞬态键不入库 + 30 天保留期）✓ |
| toc_cache | 换源/删书/刷新时定点清理，无无界增长路径 ✓ |
| 启动 DB 备份 ×5 | 设计本身合理；此前 6GB 占用的根因（vars 膨胀）已除 ✓ |

## 三、维持现状（交付说明第六节已列，此处不重复展开）

`/assets` 未鉴权（需签名 URL 方案）、源书正文缓存无 TTL（M13，等产品判据）、
PDF 封面仅内嵌 JPEG/JP2、JPEG2000/JBIG2 解不开、EPUB3 扩展元数据、
SSRF 重定向残余。另有一项早期注意到未立项的：**离线书架缓存把陈旧数据当实时展示**，
改法是加时间戳 + 前端「离线数据」标记，属小改动。

## 四、建议的动手顺序

1. **索引三条**（几行代码，立即受益，零风险）
2. **词典懒加载**（438KB gzip 不再上首屏，改动局部）
3. **警告清零**（半小时的卫生活，顺手把 6 处 namespace 意图写明）
4. **element-plus 按需**（收益最大但要过一遍全部页面回归，放在有整块时间时做）
5. **书架更新检查并发化**（做之前先确认用户书架规模是否已经到了会疼的量级）
